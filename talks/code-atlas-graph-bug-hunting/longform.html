What is the need?

  • Bugs in larger codebases aren't obvious until relationships are traced across modules
  • Only so much information can fit in context and attention
  • API contracts drift
  • Docs become stale (or confidently mask stale code)
  • Dependency and data flows don't always stick out easily
  • The result: hidden bugs that don't surface without deeper introspection

Why Graphs?

  • Graphs track relationships – many ways to view code as a graph
  • Developers think in graphs
  • AST, filesystem layout, call stack, data flow, dependencies, user scenarios, CI processes
  • But LLMs don't naturally "think" about code this way
  • By asking the LLM to build graphs, it structures information in ways that cause it to look at the code differently

Graph-Building Finds Bugs

Building docs for user-data flows kept turning up bugs that were buried deep (e.g. silently trimming an array to one element in a return).

Asking questions like "look for more bugs of this type" led to the LLM looking at adjacent categories altogether.

Experiment: GraphViz and the AST

  • Graphviz is a text-to-graph rendering library
  • DOT language format – very expressive
  • Difficult to learn but common in the training set
  • Can render to SVG, PDF, interactive JS
  • Asking the LLM to use treesitter+Graphviz found new bugs!

Mermaid: Markdown Integrated Diagramming

  • Mermaid works natively in GitHub – the LLM knows it well
  • Less expressive than DOT, but also less complex
  • Could I get the same effect from Mermaid diagrams?

Mermaid vs Graphviz: Results

Testing across multiple repos showed both Mermaid and Graphviz triggered bug discoveries, with Graphviz finding additional issues in some repos due to its greater expressiveness.

Bonus: Create Docs at the Same Time

By making diagrams of the code from different points of view it helps create good docs.
